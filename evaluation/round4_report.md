## 0. 무엇을 평가했나

M5에서 질의 모드의 점검 단계를 ReAct 점검 에이전트로 바꿨다 (SERVICE.md 10.5, TASKS 5-2~5-5). 배치는 고정 순서 그대로다.

| | 3차 (고정 순서) | 4차 (ReAct) |
|---|---|---|
| 점검 단계 | `retrieve_checklist → coverage_check` | `retrieve_checklist`(첫 검색) → 점검 에이전트 ↔ 도구(`search_checklist`, `get_checklist_item`, 최대 4회) → 판정 체인 → 검증 |
| 판정 근거 | 첫 검색 5개 | 첫 검색 5개 + 도구가 돌려준 항목 |

- 고정 순서 쪽은 다시 돌리지 않고 3차 최종 결과를 기준으로 쓴다 (사용자 결정: 같은 수치를 다시 재는 비용을 줄임).
- **이력 참고는 껐다** (`use_history=False`). 질의 모드도 최근 판정을 DB에서 읽어 참고하는데, DB 내용에 따라 결과가 바뀌면 3차와 같은 조건이 아니게 되기 때문이다.
- 시험지(`test_queries.csv`)와 채점 프롬프트는 바꾸지 않았다.

### 채점 코드 수정 1건

첫 실행은 **8/21**로 나왔다. 실패 13건 중 12건이 "단계 coverage_check 실행 실패"였다. 시험지의 `expected_tools`가 고정 순서 단계 이름(`coverage_check`)으로 적혀 있는데, ReAct에서는 같은 역할의 단계 이름이 `coverage_react.judge`이기 때문이다. 채점관(LLM) 판정은 4번을 빼고 모두 통과였다.

- `run_eval.py`: `STEP_ALIASES = {"coverage_check": {"coverage_react.judge"}}` — ReAct 판정 단계도 점검을 실행한 것으로 본다. `retrieve_checklist`는 ReAct에서도 첫 검색으로 그대로 실행되므로 별칭이 필요 없다.
- `--rescore`가 코드 검사도 다시 계산하도록 고쳤다 (LLM 채점 판정은 저장된 값을 쓰고, RAGAS 지표는 다시 계산).
- 시험지를 고치지 않은 이유: 시험지는 "점검을 했는가"를 묻는 것이지 노드 이름을 묻는 것이 아니다. 단계 이름은 구현이 바꾼 것이므로 채점 코드에서 맞춘다.

## 2. 실패 사례

### 4번 (positive) — 위탁 콜센터 상담 기록 유출 (3차와 같은 실패)
- 경로: **상한 도달** — `get_checklist_item(2.3.1) → search_checklist(수탁자 보안 관리 실태 점검) → search_checklist(위탁업체 감독 이행점검) → get_checklist_item(3.3.2)`
- 에이전트는 "수탁사 점검"을 다루는 항목을 찾으려고 두 번 재검색하고 3.3.2 원문까지 열었다. 그래도 판정은 "수정 필요 (2.3.1)"이고 3.3.2는 인용하지 않았다.
- 판정 사유: "위탁 이후 수탁사에 대한 주기적 점검·감독 의무가 체크리스트에 명시되어 있지 않다." 이 판본의 3.3.2는 위탁 사실 **공개** 중심이라 이 판단은 체크리스트 내용과 맞다. 2차 결정대로 기대값을 유지하고 실패로 남긴다.
- ReAct가 한 일: 3차는 3.3.2가 검색 결과에 있는데 인용하지 않았다. 4차는 **더 찾아보고, 원문을 열어 본 뒤에** 같은 결론을 냈다. 결과는 같지만 "체크리스트에 없다"는 판단의 근거가 더 단단해졌다.

### 6번 (positive) — 개인정보 처리방침 작성지침 개정 (새 실패)
- 경로: **재검색** — `get_checklist_item(3.5.1) → search_checklist(자동화된 의사결정 프로파일링) → search_checklist(인공지능 알고리즘 처리 기준)`
- 3차: "⚠️ 수정 필요 (3.5.1)" + 제안 1건 (자동화된 결정 기준 공개 의무를 점검내용에 추가).
- 4차: "✅ 있음 (3.5.1)", 제안 없음 → 코드 검사 "단계 draft_proposals 실행 실패". 채점관은 통과로 봤다 (시험지 traits에 판정값이 정해져 있지 않음).
- 원인: 에이전트가 3.5.1 원문을 열었고, 확인사항 1번의 **"법령에서 요구하는 내용을 모두 포함하여 … 작성하였는가"** 를 근거로 판정 체인이 "새 법령 요구도 이 문구로 점검 가능하다"고 봤다.
- 판단: 이 근거대로라면 처리방침에 관한 어떤 법 개정도 늘 "있음"이 되어, 체크리스트를 고칠 일이 생기지 않는다. 정책 변경 기사에서 **새 의무를 점검하는 구체 문구가 있는지**를 보려는 이 서비스의 목적과 맞지 않으므로 **회귀로 본다.**
- 원문을 열면 확인사항까지 보이는데, 확인사항에 있는 "법령 요구 내용 모두 포함" 같은 **포괄 문구**가 근거로 쓰인 것이 원인이다. 고정 순서에서도 판정 체인은 같은 원문을 받지만, 조사 메모가 이 문구를 강조하면서 판정이 기운 것으로 보인다.
- 개선안 (사용자 확인 후 반영): 점검 프롬프트(`coverage_check.md`)에 "‘법령에서 요구하는 내용을 포함’ 같은 포괄 문구만으로는 새 법령 요구를 다룬다고 보지 않는다. 새 의무 자체를 점검하는 문구가 없으면 ‘수정 필요’"를 추가하고 6번과 정책 사례(13번 등)를 다시 돌린다. 고정 순서·ReAct가 같은 기준을 쓰므로 배치에도 적용된다.

## 4. 결론

- **품질**: 통과율 95% → 90% (6번 1건 회귀), 가드레일 4/4 유지, RAGAS 4개 지표 동일. 성공 기준은 모두 충족한다.
- **비용**: 점검 사례당 약 +7.5초 (+36%), LLM 호출 +2.2회.
- **얻은 것**: 에이전트가 근거가 애매할 때 원문을 확인하고, 없으면 다른 표현으로 다시 찾는다. 4번처럼 "체크리스트에 없다"는 판단이 더 찾아본 뒤에 나오고, 그 과정이 trace에 남아 사용자가 어떤 항목을 확인했는지 볼 수 있다.
- **잃은 것**: 원문의 포괄 문구가 근거로 쓰여 판정이 "있음" 쪽으로 기울 수 있다 (6번). 시간과 호출 수가 늘었다.
- **ReAct가 3차보다 눈에 띄게 나쁜가**: 아니다 — 1건 차이이고 원인이 분명하다. 다만 회귀 1건이 있으므로 질의 모드 기본값(react 유지 여부)과 6번 개선안 반영 여부는 사용자와 정한다 (TASKS 5-6 확인 기준).
